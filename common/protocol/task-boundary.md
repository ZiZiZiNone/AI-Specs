# 任务边界

> 路径基准：本文所有裸路径相对规范库根 `<SPEC_ROOT>` 解析。见 `<SPEC_ROOT>/README.md`「路径基准」。

宪法 C6 的细则。C6 管**该不该做这一步**，不管这一步写得好不好。
代码质量由对应子树的规则与自检清单管（前端：`frontend/rules/`、`frontend/checklists/`），
两者互不替代。

## 授权面三档

任何任务开工前先确定授权面，写进输出模板的「范围/边界」。
拿不准就是**只读档**，不是开放写档。

| 档位 | 允许的动作 | 默认适用 |
|---|---|---|
| **只读** | 读文件、检索、执行只读命令、输出结论 | Review、答疑、诊断、评估、复盘 |
| **定向写** | 只写已列明的文件，加上真实调用链上被迫改的文件 | Bugfix、小范围 Refactor |
| **开放写** | 在需求描述的范围内新建与修改 | Feature、用户明确授权的整体重构 |

**升档必须由用户明确表示**，不能由 AI 自行推断。
「顺手」「既然已经看到了」「不改会有隐患」都不是升档理由——它们是报告内容，不是动作依据。

**降档不需要授权**：任何时候都可以把待写的动作改成「报告并等待」。

**定向写档的调用链例外**：修共享函数时必须一并改真实受影响的调用方、fixture 与测试
（`frontend/tasks/bugfix.md`：「检查所有调用方（修共享函数而非单点）」）。
这不是范围外扩，是完成需求的必要后果。判据是「不改它，当前需求就不成立」。

## 消费者判据（四问）

要加一个用户没点名的东西时，依次问：

1. 用户要求了吗？
2. 不做它，当前需求能否成立？
3. 哪一段可达的代码、数据、接口、验收条件会**消费**它？指得出具体位置吗？
4. 省掉它，当前验收会失败吗？

四问全否 → 不实现，可作为建议报告。
第 3 问指不出具体消费点，只能说出「以后可能有用」「更健壮」→ 视同全否。

这条判据与 `common/rules/reusability.md`「任何情况下不为"未来可能"预造抽象」、
`frontend/tasks/feature.md`「不做需求外的功能（YAGNI）」同源，四问是它们的可验伪化：
YAGNI 是态度，指不出消费点是事实。

**判据不是「越少越好」**：必要的调用方、测试、无障碍、安全、兼容与迁移工作，
只要第 3 问指得出消费点就必须做。目标是最小的**正确**结果，不是最小的 diff。

## 四类越界

### 一、范围外扩
需求是一个点，动作扩成一片。已有条款：
`frontend/tasks/bugfix.md`「不顺手改无关代码」、`common/rules/refactor.md`「一次重构只做一件事，避免夹带功能改动」。

典型形态：修一个字段顺手重排整个文件；改一个组件顺手升级依赖；
为对齐风格批量改动未被需求触及的文件（另见 `AGENTS.md` B3 禁止逐文件格式化）。

### 二、无消费者产物
产物存在，但全项目没有一处读取它。
本库已有实证条目：`frontend/examples/golden/anti-examples.md`「## 5. retryable 计算了但没人用」——
「字段成为装饰。规范要求的不是"有这个字段"，而是"重试策略由它驱动"。」

同类形态：算出来不用的派生值；建了不生效的 guard；
为不存在的输入写的兼容分支；无人调用的配置项与开关；
为想象中的未来加的抽象层、迁移脚本、feature flag。

判定方式：指名消费者。指不出即为装饰性代码，删除。

### 三、意图越界
用户要的是结论，AI 直接动手改代码。
只读档下任何写动作都属越界，包括「顺手修一个明显的笔误」。

正确处理：把它写进报告，标注严重度与位置，等用户决定。
用户随后要求修改时，任务类型切换为 Bugfix 或 Refactor，重新声明授权面。

### 四、重复取证
同一事实已有足够证据，仍反复检索、重读、重跑、重审。
已有条款：`AGENTS.md` B1「禁止无计划反复小段重读」、
B4「禁止反复猜测、推演、防御不存在的问题」。

停止条件：该结论所依赖的每处事实都已有一次可复现的证据（命令 + 结果或原文摘录）。
此时继续取证不增加正确性，只消耗预算。

与 `common/protocol/final-gate.md`「必须实际执行构建/类型检查/测试」不冲突：
后者要求**至少执行一次**，不要求执行多次。一次通过即为已验证，重跑需给出重跑理由
（如改动后需重验、上次执行环境不同）。

## 交付文本同样适用

文本里的一句话也要有消费者：这句话改变读者的哪个决定？

**删除**：无决策用途的免责声明、对未被提出的批评的预先辩解、
自证勤勉的过程叙述（「我检查了多个文件」「这不是完整分析」）、
把内部风险控制翻译成面向用户的泛化告警。

**保留**：用户要求的说明；影响读者判断的实质限制；
`common/protocol/final-gate.md` 要求的未验证项声明与 `common/rules/test.md` 要求的 mock 数字标注——
这三类都有明确消费者（用户据此决定是否补跑、是否采信数字）。

**改写而非堆叠**：结论不确定时收窄陈述范围或标注依据强度，
不要在正确结论后追加一串弱化句。C1 要求标注"待确认"，指的是具体的待确认项，
不是笼统的免责。

## 与任务类型的映射

| 任务类型 | 默认授权面 | 边界要点 |
|---|---|---|
| Feature | 开放写（限需求范围） | 四问用于拦截需求外功能 |
| Bugfix | 定向写 | 改动点 + 真实调用链；不夹带重构 |
| Refactor | 定向写 | 行为不变；不夹带功能改动 |
| Review | **只读** | 只报告不修改；升档需用户明确要求 |

任务类型判定见 `common/protocol/task-analysis.md`，输出模板见 `frontend/tasks/` 对应文件。
