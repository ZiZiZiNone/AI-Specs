# 需求完整性检查

路径基准：本文所有裸路径相对规范库根 `<SPEC_ROOT>` 解析。见 `<SPEC_ROOT>/README.md`「路径基准」。

依据 `COM-007`（`common/rules/constitution.md`「核心条款」）与 `AGENTS.md` `FE-000`、`FE-004`，动工前必须对需求做完整性核验。本文件为「阻塞项与非阻塞项判定」的唯一定义源。

## 检查项

1. **目标与验收标准**：预期行为、成功判据、边界输入与失败表现是否明确？
2. **契约与数据模型**：涉及的接口路径、请求/响应字段、错误码、持久化字段与兼容要求是否明确？
3. **权限与安全边界**：谁能操作、涉及哪些资源归属校验、是否含敏感数据脱敏或审计要求？
4. **影响范围与约束**：技术栈、既有代码约定、性能/并发指标、截止/兼容窗口是否明确？

## 阻塞项与非阻塞项判定

- **阻塞项（必须先问清，禁止猜测开工）**：缺失后会导致**架构返工、接口/Schema 不兼容、安全越权或验收口径根本分歧**的信息。典型例子：核心业务目标不明、多义需求互斥、接口核心字段或状态码未定、权限边界未定、破坏性变更是否允许停机。
- **非阻塞项（可采用规范默认值先执行并显式说明）**：不影响核心契约与架构、易于单点调整的细节。典型例子：非关键提示文案措辞、默认分页大小（20）、搜索防抖时长（300ms）、日志字段命名（按 `common/rules/observability.md`）。

## 缺失信息提问模板

存在阻塞项时，一次性集中提问（禁止挤牙膏式多轮追问），每题必须附带**推荐默认方案**与**影响范围**：

```markdown
开工前需确认以下阻塞项（如回复“按默认”，我将直接采用推荐方案执行）：
1. [问题] —— 影响：[受影响的接口/模块]；推荐默认：[方案 A]（理由：...）
2. [问题] —— 影响：[受影响的权限/数据]；推荐默认：[方案 B]（理由：...）
```

用户明确回复“你来定/按默认”后，立即按推荐默认执行并在交付说明中记录所选默认值。
