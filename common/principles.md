# 通用工程原则

路径基准：本文所有裸路径相对规范库根 `<SPEC_ROOT>` 解析。见 `<SPEC_ROOT>/README.md`「路径基准」。

本文件是前后端共享的架构总纲。具体语言目录结构见 `frontend/rules/architecture.md`、`backend/go/structure.md`、`backend/php/structure.md`。

## 总纲：极致解耦

**唯一可检验判据**：把任意一个逻辑单元、组件或服务搬到另一个宿主（不同页面、不同路由、不同框架入口、单元测试进程），**不改其内部代码能否直接工作**。

- 能直接工作 → 解耦达标。
- 必须改内部代码（删全局单例、拆路由耦合、剥离框架上下文）→ 耦合超标，必须重构。

**例外边界**：入口适配层（HTTP Controller、路由守卫、小程序 Page 胶水、框架 DI 启动装配）天然绑定宿主，但**只能做协议转换与组装**，厚度严格受控，不得承载业务判断。

## 四条通用原则

### 1. 薄入口原则
- 入口层（前端页面文件、后端 Controller/Handler）只做三件事：接收与基础格式校验、调用下层编排/服务、映射输出或状态展示。
- 禁止在入口层写业务状态机、跨实体计算、直接拼接 SQL 或直接操作底层持久化。

### 2. 模块解耦原则
- 模块间通过显式输入与输出（Props/Emits、DTO、Interface）通信，禁止隐式共享可变全局状态。
- UI 组件只渲染传入数据并发出意图事件，不直接发起网络请求、不直接读写全局 Store。
- 后端仓储（DAO/Repository）只负责数据持久化与查询映射，不承载业务规则与跨仓储事务编排。

### 3. 逻辑解耦原则
- 纯业务规则（校验、计算、状态跃迁、权限判据、分页与查询序列化）必须沉淀为无框架副作用的纯函数或领域服务，可在无 UI / 无真实数据库环境下直接跑单测。
- 同一条业务规则全系统只允许存在**唯一权威实现**，严禁在入口层、组件库配置、服务层各写一份（见 `common/rules/business-rule.md`）。

### 4. 单向依赖原则
- 依赖方向严格单向：`入口层 → 编排/服务层 → 领域逻辑/仓储接口`，底层绝不反向依赖上层。
- 禁止循环依赖（`A → B → A`）；跨模块共享契约下沉到独立类型/接口层。
- 依赖倒置：高层服务依赖抽象接口（如仓储接口、事务接口、日志接口），不依赖具体基础设施实现。

## 检查清单

- [ ] 把核心业务逻辑单元抽离到纯单元测试进程中，无需启动 Web 服务器或真实数据库即可运行
- [ ] 入口层不含业务规则分支与直接数据访问代码
- [ ] 同一业务规则不存在多处重复实现
- [ ] 模块间无循环依赖，无反向依赖上层
- [ ] 框架胶水代码被严格限制在入口适配层，未渗透进领域逻辑
- [ ] 所有外部依赖（DB、HTTP 客户端、时钟、随机数）均通过参数或接口注入，而非全局隐式获取
- [ ] 落地目录结构符合对应端规范（`frontend/rules/architecture.md`、`backend/go/structure.md`、`backend/php/structure.md`）
