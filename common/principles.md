# 通用原则

路径基准：本文所有裸路径相对规范库根 `<SPEC_ROOT>` 解析，首段为 `common/`、`frontend/` 或 `backend/`。
见 `<SPEC_ROOT>/README.md`「路径基准」。

四条通用原则，前端与后端**同等适用**。抽象层只有这四条，具体形态按语言/框架落地：

- 前端落地与量化标准：`frontend/rules/core-principles.md`（FE-101 至 FE-104）
- 后端落地：`backend/README.md`「分层原则（PHP / Go 共用）」与各子树 `structure.md`

本文不设条款级编号（COM-011 规定条款级编号只存在于 `common/rules/constitution.md` 的 COM-007 至 COM-012
与 `AGENTS.md` 的 FE-000 至 FE-005）。引用本文时写「编号 + 文件路径 + 原文逐字摘录」，或直接用小节标题。

## 极致解耦（总纲）

> 不管外部如何实现，只需要接受固定结构数据（或不需要）就能完成功能。
> —— 见 `frontend/rules/core-principles.md`「FE-102 组件完全解耦原则」

这是四条原则的共同目标，也是对前端与后端**同等强度**的要求，不是"分层清晰"的同义词。

**判定方式**：把这个单元搬到另一个宿主里（另一个页面 / 另一个 HTTP 入口 / 一个单测），
不改它内部任何代码，能否直接工作？答"不能"即为未解耦。

具体到后端，这意味着逻辑单元不接收 HTTP 对象、不自己取数据库连接、不依赖全局单例——
只接收结构化数据，返回结构化结果。

## 薄入口原则

入口只负责组装与转发，业务规则不在入口。

- 前端入口 = 页面（Page）；后端入口 = 控制器（Controller）/ 路由处理函数。
- 入口允许：接收输入、调用下层、返回结果。
- 入口禁止：业务判断、数据转换、状态计算、直接访问数据源。
- 量化标准（行数、函数数、状态数）按语言/框架定，见各子树。**数字是"职责是否单一"的可观测代理，
  不是目的**：数字达标但职责混杂仍不合规；把逻辑原样搬到下层以求达标属规避而非治理。

---

## 模块解耦原则

单元不依赖外部实现细节、不直接访问全局状态、不直接触达外部 IO。

- 依赖通过参数显式传入（前端 props / 函数入参；后端函数入参 / 构造函数注入），
  不通过全局单例、全局变量、静态门面（Facade）、服务定位器隐式获取。
- 单元自包含：完成其职责所需的逻辑都在单元内部，不依赖调用方的隐含约定。
- 禁止反向依赖：下层不得回调上层，不得读取上层的状态。

---

## 逻辑解耦原则

业务规则集中在独立的逻辑单元，与框架、UI、传输协议无关。

- 前端 = `Logic`；后端 = `Logic` / `Service`（GoFrame 的 `internal/logic`、Laravel 的 `app/Services`）。
- 逻辑单元禁止依赖宿主运行时对象：前端不得 import 框架 Hook；
  后端不得依赖 `*ghttp.Request`、Laravel 的 `Request` / `Response`。
- 逻辑单元必须可脱离宿主单测：前端不挂载组件，后端不起 HTTP 服务。
- 输入输出用明确的数据结构定义，不传宿主对象，不返回宿主对象。
- 同一业务规则只实现一份，多处复用同一逻辑单元。

---

## 单向依赖原则

依赖方向唯一且向下，禁止向上、反向与循环。

| 端 | 依赖方向（概念层） | 唯一来源（改动以该文件为准） |
|---|---|---|
| 前端 | `Page/Component → Hook → Logic → Service` | `frontend/rules/core-principles.md`（FE-104 单向数据流原则） |
| 后端 | `入口 → 业务（Logic / Service）→ 数据（DAO / Repository）` | `backend/README.md`「分层原则（PHP / Go 共用）」 |

后端的具体落地形态因框架而异，见 `backend/README.md`「分层原则（PHP / Go 共用）」与各子树 `structure.md`，不可套用同一条线性链条。

本表只列方向概览，**细节与改动以「唯一来源」列为准**，避免同一结论两处各写一遍而漂移。

- 允许跨层直连（如前端 Page 直调 Logic、后端 controller 直调 service）与同层组合，禁止反向。
- 数据自上而下传入，结果自下而上返回。
- 不制造纯转发层：某层删掉后若没有任何业务规则随之丢失，它就不该存在。

## 检查清单

- [ ] 入口无业务判断（薄入口）
- [ ] 依赖显式传入，无全局单例 / 静态门面 / 服务定位器
- [ ] 业务规则集中在逻辑单元，逻辑单元不依赖宿主框架对象
- [ ] 逻辑单元可脱离宿主单测
- [ ] 同一业务规则只有一份实现
- [ ] 依赖方向唯一向下，无反向 / 循环依赖
- [ ] 无纯转发层
