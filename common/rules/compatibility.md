# 向后兼容与数据演进规范（COM-016 细则）

路径基准：本文所有裸路径相对规范库根 `<SPEC_ROOT>` 解析。见 `<SPEC_ROOT>/README.md`「路径基准」。

数据库大表在线 DDL 与锁表实操见 `backend/patterns/migration-online-ddl.md`。

## 1. Expand-Contract（先扩后缩）双阶段策略
滚动发布或灰度期间，新旧两版应用代码会同时访问同一数据库、缓存与消息队列。凡涉及破坏性变更（字段改名、改类型、删列、改消息格式、改 API 必填项），**禁止一步到位直接破坏旧版**，必须拆分为多阶段部署：

1. **Expand（扩展）**：新增新列/新字段/新接口，旧列保持兼容；应用层实现双写（新旧同写）或兼容双读。
2. **Backfill（回填与校验）**：分批限速回填历史数据，校验新旧数据一致性。
3. **Switch（切换）**：全量应用切到读新写新，观察一个完整业务周期无回滚需求。
4. **Contract（收缩）**：在确认无任何旧版实例与下游消费者依赖后，删除旧列、旧字段与兼容代码（按 `FE-005` 删净）。

## 2. 接口与消息体兼容原则
- **只增不删，只松不紧**：同主版本内只允许新增**可选**请求字段与响应字段；禁止缩小枚举范围、将可选字段改为必填、或改变既有字段的数据类型/单位。
- **未知字段宽容**：反序列化外部请求或事件消息时，对未识别的新增字段保持忽略而非报错（除非明确做安全白名单校验的排序/过滤字段）。

## 3. 不可逆操作保护与回滚预案
- 任何涉及 `DROP TABLE`、`DROP COLUMN`、数据物理删除或不可逆格式覆写的变更，提交前必须附带：
  1. 备份/快照策略；
  2. 明确的回滚步骤（或显式说明不可逆窗口与止损方案）；
  3. 停机/锁表影响评估。

## 检查清单

- [ ] 滚动发布窗口内，旧版本代码可正常运行在新 Schema/消息格式之上
- [ ] 破坏性改名/删列已拆分为 Expand → Backfill → Switch → Contract
- [ ] 变更附带可执行的回滚方案或应急止损说明
