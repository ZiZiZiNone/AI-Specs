# 测试

测试验证行为而非覆盖率。

## 规则
- 测试关注关键行为与业务规则（Logic/Service/关键交互），不为凑覆盖率写测试。
- 优先测纯逻辑（Logic、Service 数据转换），UI 交互按需。
- 测试命名描述行为：should_xxx_when_xxx。
- 关键分支、边界、错误路径必须有断言。
- 边界值须包含临界点本身（「恰好等于上限」应通过），用于暴露 `>` / `>=` 类错误。
- 可逆操作须有互逆断言（序列化↔解析、编码↔解码往返一致）。
- 不测实现细节（前端：内部函数、DOM 结构；后端：私有方法与内部实现），测行为结果。

## 测试必须被执行

写完测试不等于通过测试。交付前须实际运行测试与类型检查；
运行不了（环境缺失、无沙箱等）时，按 common/protocol/final-gate.md 的
「无法验证时的处理」显式声明未验证项，不得以"代码已写完"当作完成。

## Mock 与假数据

**允许**为跑通链路、演示或本地开发构造 mock 后端与假数据；
这不违反宪法 C1（禁止猜测），前提是不把假数据当成事实。

**强制要求**：
- mock 代码集中放置（如 `services/mock/`），与真实 Service 同签名，便于整体替换。
- 文件头注释声明「假数据，不代表真实业务数值」。
- 交付文档（README / 验收报告 / 结论）中若引用了 mock 产生的数字，必须标注来源为 mock。
- **禁止**把 mock 数据的统计结果写进结论（如"平均响应 120ms""共 1284 条工单"）。
- mock 可注入故障（延迟、随机失败）用于验证错误态，但注入规则须可关闭且有注释说明。

```typescript
// ✅ services/mock/mockDb.ts
// 内存假后端。数据为构造的示例值，不代表真实业务数值。
// 故障注入见 mockTransport.ts 的 FAILURE_RATE，交付前置 0。
```

**判定**：
```
问：这份数据会进入用户可见的结论或文档吗？
  ├─ 是 → 必须标注为 mock，或替换为真实数据后再引用
  └─ 否（仅用于本地跑通/测试断言）→ 允许，仍需文件头声明
```
