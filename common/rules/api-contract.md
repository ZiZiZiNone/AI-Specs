# 前后端接口契约

路径基准：本文所有裸路径相对规范库根 `<SPEC_ROOT>` 解析。见 `<SPEC_ROOT>/README.md`「路径基准」。

本文件定义前后端共享的 HTTP/JSON 接口契约。前端存量接口迁移跟踪表已下沉至 `frontend/rules/api.md`，本文件保持端无关。

## REST 路径与方法

- 资源名使用复数小写连字符（`/api/v1/order-items`），禁止在路径中拼动词（`/getOrderList`）；非 CRUD 动作使用子资源动词（`POST /api/v1/orders/{id}/cancel`）。
- 严格遵循方法语义：`GET`（安全且幂等，禁改状态）、`POST`（创建或非幂等动作）、`PUT`（全量幂等替换）、`PATCH`（局部更新）、`DELETE`（幂等删除）。

## 响应信封

所有业务接口统一使用固定信封，字段名 camelCase：

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "requestId": "req_01J..."
}
```

- `code`：`0` 表示业务成功，非零整数表示业务失败。**HTTP 200 只表示传输送达，不表示业务成功**；客户端必须同时检查 HTTP 状态码与 `code === 0`。
- `message`：面向排查或展示的简明说明；失败时不得暴露内部堆栈、SQL 或表名。
- `data`：**空值语义严格统一**——无返回内容的写操作（如 `DELETE`/取消）与所有失败响应一律返回 `null`（禁止 `null` 与 `{}` 混用）；列表无数据时返回 `{ "items": [], "page": { ... } }`；单资源不存在直接返回 HTTP `404`。
- `requestId`：全局请求追踪标识，须同时透传于响应头 `X-Request-Id` 与日志上下文（见 `common/rules/observability.md`）。

## HTTP 状态码与业务码矩阵

| HTTP 状态码 | 适用场景 | 响应 `code` | 客户端处理 |
|---|---|---|---|
| `200 OK` / `201 Created` | 请求处理完成（成功） | `0` | 消费 `data` |
| `400 Bad Request` | 语法错误、JSON 解析失败、缺少必填基础字段 | 非零（如 `40001`） | 提示修正输入，禁重试 |
| `401 Unauthorized` | 未认证或凭证过期 | 非零（如 `40101`） | 触发重新登录/静默刷新，禁盲目重试 |
| `403 Forbidden` | 已认证但无权访问目标资源 | 非零（如 `40301`） | 展示无权限，禁重试 |
| `404 Not Found` | 目标资源不存在（含归属隔离隐藏） | 非零（如 `40401`） | 展示不存在，禁重试 |
| `409 Conflict` | 资源唯一冲突、乐观锁版本冲突、幂等键在途并发冲突或同键异参 | 非零（如 `40901`） | 提示冲突或引导刷新最新状态 |
| `422 Unprocessable Entity` | 语法合法但业务规则校验失败（余额不足、状态不允许流转） | 非零（如 `42201`） | 按字段或全局展示业务原因，禁自动重试 |
| `429 Too Many Requests` | 触发限流（须附 `Retry-After` 响应头） | 非零（如 `42901`） | 尊重 `Retry-After` 退避或提示稍后重试 |
| `500` / `502` / `503` / `504` | 服务端内部故障、上游异常、不可用或超时 | 非零（如 `50001`） | 仅幂等请求可按策略有限退避重试 |

> 说明：如存量系统历史约定“纯业务校验失败返回 HTTP 200 + 非零 `code`”，必须在项目契约文档中显式登记，且前端 Service 层必须仍以 `code === 0` 为唯一成功判据。

### 业务错误码分段推荐
建议采用 5–6 位数字分段：`[域/模块 2位][类别 1位][序号 2位]`（例如 `10` 订单域 + `4` 客户端/业务校验 + `01` 优惠券过期 = `10401`），严禁跨模块复用同一错误码表达不同语义。

## 分页与排序契约

### 1. 偏移分页（常规后台管理）
- 请求参数：`page`（默认 `1`，最小 `1`）、`pageSize`（默认 `20`，服务端强制截断上限如 `100`，**截断为上限而非重置为默认值**）、`sortBy`、`sortOrder`（`asc` | `desc`）。
- **排序白名单**：服务端必须对 `sortBy` 做显式白名单映射，拒绝未知字段（返回 `400`），严禁将前端字段名直接拼入 SQL `ORDER BY`。
- 响应结构：

```json
{
  "items": [],
  "page": {
    "page": 1,
    "pageSize": 20,
    "total": 128,
    "totalPages": 7
  }
}
```

### 2. 游标分页（海量数据 / 无限滚动 / 高频写入流）
- 请求参数：`cursor`（不透明字符串，首次省略）、`limit`（默认 `20`，服务端截断上限）。
- 响应结构：`{ "items": [], "nextCursor": "eyJ...", "hasMore": true }`。

## 幂等与重试契约

- 非幂等写接口（如 `POST /orders`、支付、扣款）必须要求客户端传入 `Idempotency-Key` 请求头（建议 UUIDv4 或业务唯一键）。
- **作用域隔离**：幂等键必须绑定 `(tenantId/userId, method, path, idempotencyKey)`，严禁全局共享导致跨用户冲突或探测。
- **边界行为**：
  1. 同键同载荷且上次已成功 → 返回上次缓存的结果快照；
  2. 同键但**载荷哈希不一致** → 返回 `409 Conflict`（或 `422`），严禁静默返回旧结果；
  3. 同键首次请求**尚在处理中（in-flight）** → 返回 `409 Conflict` 并提示稍后重试；
  4. 首次请求因 `5xx` 失败且确认未落库 → 释放幂等键，允许客户端使用同键安全重试；
  5. 幂等记录必须设置合理 TTL（如 24 小时），不得无限增长。
- **重试约束**：仅对幂等方法（`GET`/`PUT`/`DELETE`）或携带有效 `Idempotency-Key` 的写请求，在网络超时/`502`/`503`/`504`/`429` 下执行有限次指数退避 + 随机抖动重试；退避等待必须响应取消信号（`AbortSignal` / `context.Context`）。

## 版本化与兼容

- URL 主版本前缀 `/api/v1/...`；同主版本内只允许向后兼容的增量演进（新增可选字段、新增枚举值时客户端须有默认兜底），破坏性变更须升主版本并按 `common/rules/compatibility.md` 执行双版本共存窗口。

## 检查清单

- [ ] 所有接口使用统一信封，失败与无内容写操作 `data` 固定为 `null`
- [ ] 客户端同时判定 HTTP 状态码与 `code === 0`
- [ ] `pageSize` 超上限时截断为上限值，`sortBy` 经过服务端白名单校验
- [ ] 关键写接口支持作用域隔离的 `Idempotency-Key`，且覆盖同键异参与在途冲突
- [ ] 响应头与日志均透传 `requestId`
