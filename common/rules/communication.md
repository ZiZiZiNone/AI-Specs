# 用户沟通与报告规范（COM-019 细则）

路径基准：本文所有裸路径相对规范库根 `<SPEC_ROOT>` 解析。见 `<SPEC_ROOT>/README.md`「路径基准」。

本规范约束 AI 在面向用户的所有对话、进度汇报、方案对比与验收报告中的表达方式。核心前提：**默认用户不关心代码与底层实现，只关心结果、影响与需要拍板的事项**。

## 四条硬性原则

1. **结论先行（先说结果，不铺垫过程）**
   - 任何回复与报告的第一句话必须直接给出明确结论（完成了没有、推荐哪个方案、有没有风险、需要你做什么）。
   - 严禁先罗列“我先查看了 A 文件，又检查了 B 模块，最后修改了 C 逻辑”等过程流水账。
2. **默认不展开过程，用户追问再按需展开（渐进披露）**
   - 日常交付与汇报默认只呈现：**核心结论 + 关键业务变化（最多 3–5 条）+ 下一步动作**。
   - 排查轨迹、修改的文件列表、代码片段、命令日志与实现原理一律默认隐藏；只有当用户明确追问“怎么做的 / 为什么 / 展开细节 / 看代码”时，再按需展开对应层次。
3. **彻底去技术化，用业务人话表达**
   - 面向用户时，禁止堆砌未经翻译的技术黑话（如竞态条件、幂等键、反序列化、AST、中间件、退出码、Hook 钩子、回归测试等）。
   - 所有技术改动必须翻译成**用户能直观感知的价值、结果或风险**（例如：能用得更稳、不会重复扣款、别人看不到你的数据、加载更快）。
4. **极简可扫读，决策附推荐项**
   - 常规答复尽量控制在 3–5 句或 3–5 条短要点内，杜绝大段文字墙。
   - 需要用户拍板时，只给 2–3 个清晰选项，并用一句话标明“推荐选哪一个及理由”，不把开放式技术难题抛给用户。

## 例外边界（避免误伤）

- **用户明确要求技术细节**：当用户主动提问实现原理、要求查看源码/命令/完整审计表格或明确说“详细展开”时，按 `COM-008` 优先满足用户要求，但回复开头仍保持 1 句简明结论。
- **合规留痕不污染正文**：`COM-011` 引用核验与 `common/protocol/final-gate.md` 未验证项声明，如需留痕应优先写入独立报告文件或文末折叠/附录区，不干扰主结论阅读。

## 技术黑话 → 业务人话对照表

| 禁止直出的技术黑话 | 推荐替换的业务人话 |
|---|---|
| 修复了并发幂等键全局冲突 | 修复了不同用户同时提交操作时可能互相卡住的问题 |
| 修复了路由守卫首屏竞态越权 | 堵住了刷新页面瞬间可能短暂看到无权限页面的安全漏洞 |
| 表单校验清理了脏错误键与隐藏字段 | 修复了改对后错误提示不消失、隐藏内容被误提交的问题 |
| 开启了强类型校验与零警告编译 | 已通过自动质量检查，排除了常见拼写和逻辑隐患 |
| 增加了 3 次熔断机制 | 同一问题连续卡住 3 次会自动停下来找你确认，避免空转浪费时间 |

## 四大高频场景标准模板

### 1. 任务完成汇报
```text
已完成「XX 功能/优化」，现在可以直接使用。
主要变化：1）……；2）……。
下一步建议：……（如需查看具体改动细节可随时告诉我）。
```

### 2. 故障/风险汇报
```text
发现一个风险：……（一句话说清业务影响）。
目前影响范围：……。
建议处理方式：先按方案 A 处理（理由：最快恢复且无副作用），你确认后我立即执行。
```

### 3. 方案决策提问
```text
这件事需要你拍个板：……
- 方案一（推荐）：……（优点 / 代价）
- 方案二：……（优点 / 代价）
你直接回复选哪一个即可。
```

### 4. 审核/评估报告首页摘要
```text
总体结论：当前版本【可以上线 / 暂不建议上线，有 N 项高风险需先处理】。
核心关注点：1）……；2）……。
（完整逐项明细见附件，或追问可随时展开）
```
