# 巨型组件

对齐关系：见 `frontend/rules/core-principles.md` P2 组件完全解耦原则，本文件阈值数字全部引用该文件及配套决策原文，不自立阈值。

## 定义

单个组件承担多个职责、或自取数据自持业务状态即为巨型组件。

## 判定信号

### 可观测信号（引用 `frontend/rules/core-principles.md` 与配套决策原文数字）

- 全库统一阈值：页面 300 行 / 函数 3 个 / 状态 5 个；组件 300 行 / props 8 个；Hook 150 行 / 成员 10 个；“禁止以搬运换达标”。

- 组件文件“一般组件：不超过 300 行”，超标即“大概率职责不单一，必须重新审视”。

- props 超过 8 个必选参数即审视职责，聚合对象计 1 个须满足三条件，否则按字段数计。

- 组件内状态变量超过 10 个、或嵌套层级超过 5 层即必须拆分（见“组件拆分决策”量化标准）。

- 组件内直接 import Store、或发起业务数据请求即违规，不看行数直接判不合规。

### 症状（命中 2 条即进入对策）

- 渲染与逻辑缠在一起，难复用、难测试，改动一处影响多处。

- props 爆炸：为省拆分把无关状态塞进一个对象，组件内逐字段各自处理。

- 组件自取详情、自持与外部平行的状态，外部重置时内部不变。

- 拆分会增加复杂度时无注释说明保留原因，直接以行数达标为由通过。

## 对策（拆到哪层，四选一写明）

- 独立区块 → 子组件：表格 / 表单 / 卡片按区块拆，判据见 `frontend/protocol/decision-trees.md`“组件拆分决策”。

- 可复用渲染 → 子组件：重复渲染逻辑提取为可复用组件，数据经 props 传入。

- 状态与副作用 → Hook：加载、弹窗、校验各归其 Hook，组件只接收数据和回调。

- 可判定规则 → Logic：展示用判定下沉纯函数，模板只查表不写条件表达式。

- 候选并列（交用户定）：A. 按区块拆子组件；B. 先抽 Logic 再看是否仍需拆组件。职责边界不同，选用由用户定。

## 正例指针

- `frontend/examples/golden/list-page.md`「6. 页面只做组装」：组件只接收数据和回调，给什么渲染什么，判定调用 Logic；表单展示与校验规则分离，规则不在组件内；通用反馈组件只管渲染，不管取数。

## 反例指针（`frontend/examples/golden/anti-examples.md`，标题原文引用，不编新条号）

- 「2. 展示型组件自己加载数据」：弹窗内部发请求取详情。

- 「6. 受控组件自持一份状态」：props 初值外另存三份 state。

- 「11. Logic 层空转」：业务规则散落在组件里，Logic 未承接判定。

## 自检指针（`frontend/checklists/detailed-check.md`，用小节名）

- “P2 组件完全解耦原则”：8 项全过，重点查无 import Store、无业务数据请求。

- “巨型组件”：职责单一、props 上限、按职责拆分三项。

- “P4 单向数据流原则”：数据经 props 下、事件经回调上，无反向依赖。

- “状态来源”：受控组件无 `initialXxx` 式双写入点。

## 决策指针（`frontend/protocol/decision-trees.md`，指针短语）

- “组件拆分决策”：先看行数，再看区块、复用、交互、props 依次判定。

- “组件自持状态决策”：业务组件、复合组件、涉数据请求一律不许自持。
