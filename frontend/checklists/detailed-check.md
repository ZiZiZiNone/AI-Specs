# 详细自检清单

所有代码提交前必须通过此清单。

## 适用性判定（先做这一步）

本清单按"完整业务功能"编写。实际任务常只涉及其中一部分，
逐条硬套会产生大量"不适用却被标成通过"的假合规。

**执行方式**：每条只有三种结论——
- **通过**：已满足。
- **不适用**：本次任务不涉及该场景（如纯 Logic 重构不涉及"五态齐全"）。
  须写明不适用的原因，一句话即可。
- **未通过**：必须修复，或按 `common/protocol/final-gate.md`「无法验证时的处理」"禁止默认视为通过"记录偏离并说明理由。

**禁止**把不适用项标成通过；也禁止把未通过项含糊为不适用。

**常见不适用范围**：

| 任务类型 | 通常不适用的章节 |
|---|---|
| 纯 Logic / 工具函数 | 四（UI 状态）、六（表单）、十（性能优化时机） |
| 纯样式调整 | 三（状态管理）、五（错误处理）、七（异步） |
| Bugfix（单点修复） | 十四（文档）；其余按改动触及面判定 |
| 新增完整功能 | 全部适用 |

**验证类条目不可用"不适用"跳过**：构建、类型检查、测试执行属于交付底线，
执行不了要按 `common/protocol/final-gate.md`「无法验证时的处理」"禁止默认视为通过"显式声明。

**任务边界类条目同样不可跳过**：授权面适用于所有任务类型，无"不适用"情形。

## 〇、任务边界检查（COM-012，先于代码质量）

本章判定"该不该做这一步"，与后续各章的"做得好不好"互不替代。
判据与四类越界见 `common/protocol/task-boundary.md`「四类越界」："需求是一个点，动作扩成一片"等四类形态，指不出消费者即装饰性代码。

### 授权面
- [ ] 已声明本次授权面（只读 / 定向写 / 开放写），并写进交付的「范围/边界」
- [ ] 未自行升档（"顺手""不改有隐患""用户没反对"都不是升档理由）
- [ ] 只读档任务（Review / 答疑 / 诊断 / 评估 / 复盘）全程无写动作

### 范围
- [ ] 改动文件均在需求范围或真实调用链上，无顺手改动的无关文件
- [ ] 未夹带重构（Bugfix）／未夹带功能改动（Refactor）
- [ ] 未逐文件格式化（FE-003）

### 消费者
- [ ] 用户未点名的每处产物都指得出具体消费点（代码/数据/验收条件的位置）
- [ ] 无装饰性产物：算了不用的派生值、不生效的 guard、无人读取的字段与配置、
      为不存在的输入写的兼容分支、为想象中的未来加的抽象与开关
- [ ] 未为"未来可能"预造抽象（见 `common/rules/reusability.md`「抽象决策」："任何情况下不为"未来可能"预造抽象"）。

### 取证
- [ ] 同一事实取证一次即止，无反复检索、重读、重跑、重审
- [ ] 已列出本次已读规范文件与触发依据（必读四件 + 按需触发点），未全量通读；并行调用已去重
- [ ] 重跑验证的都给出了重跑理由（改动后重验 / 环境不同）

### 交付文本
- [ ] 无无决策用途的免责声明与预先辩解
- [ ] 无自证勤勉的过程叙述（"我检查了多个文件""这不是完整分析"）
- [ ] 保留了有消费者的声明：未验证项（见 `common/protocol/final-gate.md`「无法验证时的处理」："禁止默认视为通过"）、mock 数字标注（见 `common/rules/test.md`「Mock 与假数据」："交付文档中若引用了 mock 产生的数字，必须标注来源为 mock"）、
      影响读者判断的实质限制

## 一、核心原则检查（必须）

本章阈值（300/500 行、3 个函数、5 个状态等）是职责是否单一的可观测代理，判定顺序见 `frontend/rules/core-principles.md`「指标的意图」："判断顺序始终是先看职责，再看数字"，"特别禁止：以搬运换达标"。

### FE-101 页面薄层原则
- [ ] 页面文件不超过 300 行（纯展示类不超过 500 行）
- [ ] 页面内直接定义的函数不超过 3 个
- [ ] 页面内状态变量不超过 5 个
- [ ] 达标方式不是"把函数原样搬进 Hook"（见 `frontend/protocol/decision-trees.md`「二之二、Hook 拆分决策」："是否只是把页面函数原样搬了进来？是 → 不合规"）。
- [ ] 页面内无业务判断逻辑（if/switch 判断业务规则）
- [ ] 页面内无数据转换逻辑（map/filter/reduce 转换数据结构）
- [ ] 页面内无接口调用（fetch/axios）
- [ ] 页面内无复杂交互逻辑

### FE-102 组件完全解耦原则
- [ ] 所有组件 props 有 TypeScript 类型定义
- [ ] 组件内无 import Store
- [ ] 组件内无 import Service
- [ ] 组件内无数据请求（fetch/axios）
- [ ] 组件不访问路由参数（除页面组件）
- [ ] 组件不访问全局变量（除自包含交互组件）
- [ ] 数据通过 props 传入，事件通过回调上报
- [ ] 自包含交互组件在白名单内（Input/Select/Checkbox 等）

### FE-103 逻辑完全解耦原则
- [ ] Logic 文件无 import UI 组件
- [ ] Logic 文件无 import 框架 Hook（useState/useEffect）
- [ ] Logic 可调用 Service，但不直接调用 axios/fetch
- [ ] Logic 可单独测试（不需要挂载组件）
- [ ] 所有公共 Logic 函数有类型定义
- [ ] Logic 按业务领域拆分，不按页面拆分

### FE-104 单向数据流原则
- [ ] 数据从页面流向组件（props 传入）
- [ ] 事件从组件流向页面（回调上报）
- [ ] 组件不能调用父组件方法（只能通过回调）
- [ ] Logic 不能调用 Hook/UI
- [ ] 依赖只能向下（Page/Component→Hook→Logic→Service）
- [ ] 无反向依赖、无循环依赖

## 二、架构层次检查

### Page 层
- [ ] 只做组件组装和数据传递
- [ ] 不包含业务逻辑
- [ ] 不直接调用接口
- [ ] 状态管理清晰（局部/Store）

### Component 层
- [ ] 职责单一（能用一句话描述）
- [ ] props 数量不超过 8 个
- [ ] 组件文件不超过 300 行
- [ ] 只负责展示和交互
- [ ] 不承载业务逻辑
- [ ] 不直接访问接口

### Hook 层
- [ ] 只在需要 UI 框架能力时使用
- [ ] 内部调用 Logic 完成业务
- [ ] 不直接写业务逻辑
- [ ] 管理 UI 状态（loading/error/data）
- [ ] 处理副作用（请求/定时器）
- [ ] 单文件 ≤150 行，对外暴露成员 ≤10 个
- [ ] 关注点单一，职责可用一句话描述
- [ ] 非"页面搬运产物"：抽出的单元可被另一处复用或单测
- [ ] 无"万能 Hook"（同时管列表+表单+详情+权限）
- [ ] 副作用有对应清理（取消请求/清定时器/解绑监听）

### Logic 层
- [ ] 框架无关（不依赖 React/Vue）
- [ ] 可单独测试
- [ ] 按业务领域拆分
- [ ] 单一职责
- [ ] 有明确的输入输出类型
- [ ] 非空转：可判定的业务规则确实落在此层，而非散在页面/组件

### Service 层
- [ ] 唯一的接口访问入口
- [ ] try-catch 收敛在统一请求出口，业务方法内不重复包裹
- [ ] 返回统一的 Result 类型
- [ ] 参数校验、响应转换在 Service 内
- [ ] 错误统一归一为 StandardError
- [ ] 所有方法可接收外部 signal（供上层取消）
- [ ] 超时与外部取消合并为同一 signal
- [ ] 非幂等方法（POST 等）默认不重试

## 七、异步操作检查

### 防抖节流

- [ ] 非临时性错误不自动重试
- [ ] 重试期间外部取消能立即中断

### 请求取消
- [ ] 组件卸载时取消未完成请求
- [ ] 快速切换时取消旧请求

## 使用说明

### 提交前检查流程
1. 先做「适用性判定」，划出本次任务的适用章节
2. 逐项检查代码，每条给出 通过 / 不适用（附原因）/ 未通过
3. 不符合项立即修正
4. 执行构建、类型检查、测试；执行不了则按 `common/protocol/final-gate.md`「无法验证时的处理」"禁止默认视为通过"声明
5. 全部通过后提交

### 检查频率
- **必须**：每次提交前
- **建议**：实现过程中定期检查
- **推荐**：Code Review 时使用

### 不确定时
- 查阅对应规范文档（`frontend/rules/` 各规则文件，按需打开原文核对）
- 查阅决策流程图（见 `frontend/protocol/decision-trees.md`「props 计数规则」："对象内字段属于同一关注点，不是无关状态的拼盘"等三条件，按章取用）
- 查阅参考写法（`frontend/examples/golden/`），负向对照见 `frontend/examples/golden/anti-examples.md`「1. 页面直接调用 Service」："页面 import Service，并在事件处理里直接发请求 + 手写反馈"为违规对照
- 向用户确认
- 禁止猜测
