# 决策流程图

路径基准：本文所有裸路径相对规范库根 `<SPEC_ROOT>` 解析。见 `<SPEC_ROOT>/README.md`「路径基准」。

将复杂判断转化为明确的决策流程。

## 一、状态归属决策

### 决策流程
```
开始
  ↓
问：只在单个组件内使用？
  ├─ 是 → 组件内局部状态
  └─ 否 ↓
问：父子组件需要共享？
  ├─ 是 → 提升到父组件，props/回调下发
  └─ 否 ↓
问：仅兄弟组件共享？
  ├─ 是 → 提升到共同父组件
  └─ 否 ↓
问：跨页面或跨模块共享？
  ├─ 是 → 进入 Store
  └─ 否 → 重新审视是否真的需要共享
```

### 量化标准
- **单个组件内**：该状态仅影响当前组件的渲染和行为
- **父子共享**：直接父子关系，层级不超过2层
- **兄弟共享**：有共同父组件，且父组件层级不超过3层
- **跨页面/跨模块**：不同路由页面，或不同业务模块

### 特殊场景判定
| 场景 | 判定 | 原因 |
|------|------|------|
| Modal/Drawer 状态 | 触发组件内状态 | Modal 是临时 UI，不是独立页面 |
| Tab 切换状态（需保留） | URL 参数 | 需要跨 Tab 保持且刷新后可分享 |
| Tab 切换状态（不需保留） | 父组件状态 | 切换即重置 |
| 表单草稿（需保留） | URL 参数或 LocalStorage | 需要持久化 |
| 表单草稿（不需保留） | 组件内状态 | 提交或取消即清除 |
| 列表筛选条件（需保留） | URL 参数为唯一来源 | 刷新后保持（见 `frontend/rules/store.md`「需刷新保持的状态一律以 URL 为唯一来源，不得以 Store 作为替代」） |
| 列表筛选条件（不需保留） | 组件内状态 | 刷新即重置 |

## 二、Hook vs Logic 决策

### 决策流程
```
开始：需要复用的逻辑
  ↓
问：是否需要 UI 框架能力（状态/生命周期/副作用）？
  ├─ 否 → 纯 Logic 文件
  └─ 是 ↓
问：是否需要组合多个 UI 状态（loading/error/data）？
  ├─ 是 → Hook（内部调用 Logic）
  └─ 否 ↓
问：是否需要订阅外部状态（Store/Context）？
  ├─ 是 → Hook（内部调用 Logic）
  └─ 否 ↓
问：是否需要生命周期管理（mount/unmount/update）？
  ├─ 是 → Hook（内部调用 Logic）
  └─ 否 → 纯 Logic 文件
```

### 判定标准
**纯 Logic**：
- ✅ 纯函数计算
- ✅ 数据转换
- ✅ 业务规则判断
- ✅ 状态机逻辑
- ❌ 不依赖框架 API
- ❌ 不持有 UI 状态

**Hook**：
- ✅ 组合 UI 状态（loading/error/data）
- ✅ 调用 Logic 完成业务
- ✅ 订阅外部状态
- ✅ 管理副作用（网络请求/定时器）
- ✅ 生命周期管理
- ❌ 不直接写业务逻辑

### 示例对照
| 需求 | 选择 | 原因 |
|------|------|------|
| 计算订单总价 | Logic | 纯计算，无 UI 状态 |
| 校验表单字段 | Logic | 纯判断，无 UI 状态 |
| 加载用户数据 | Hook | 需要 loading/error/data 状态 |
| 轮询接口 | Hook | 需要定时器和生命周期管理 |
| 格式化日期 | Logic | 纯函数 |
| 防抖搜索 | Hook | 需要定时器和状态管理 |

## 二之二、Hook 拆分决策

Page 有量化约束、Hook 若没有，页面瘦身就会把复杂度堆进不受审查的 Hook。
本节与 frontend/rules/core-principles.md 的 Hook 量化标准配套使用。

### 决策流程
```
开始：Hook 超过 150 行 或 暴露成员超过 10 个 或 难以一句话描述职责
  ↓
问：是否混合了多个关注点？
  （数据加载 / 表单状态 / 弹窗开关 / 行操作 / 异步校验 算不同关注点）
  ├─ 是 → 按关注点拆分为多个 Hook
  └─ 否 ↓
问：内部是否包含可脱离框架的纯计算或判断？
  ├─ 是 → 下沉到 Logic，Hook 只保留状态与副作用
  └─ 否 ↓
问：是否只是把页面函数原样搬了进来？
  ├─ 是 → 不合规。重新按关注点组织，或下沉到 Logic
  └─ 否 → 可保持，并注释说明保留原因
```

### 关注点清单（同一 Hook 内出现 3 个以上即须拆分）
- 一次数据加载（含其 loading/error/empty 与竞态）
- 一个表单的值与校验时机
- 弹窗/抽屉的开关与关闭前确认
- 一组行操作（确认 → 执行 → 反馈）
- 一次异步校验或异步搜索
- 一份 URL / 持久化状态的读写

### 判定标准
**合规的 Hook**：
- ✅ 职责可一句话描述（"加载工单列表并维护其五态"）
- ✅ 能被第二处复用，或能独立测试
- ✅ 内部无纯业务判断（已下沉 Logic）

**不合规（搬运式抽取）**：
- ❌ 名字叫 `usePageLogic` / `useXxxHandlers` 这类无关注点指向的聚合
- ❌ 仅为让页面函数计数达标而存在，没有第二个调用点也无法单测
- ❌ 同时持有互不相关的状态（弹窗开关 + 列表数据 + 表单错误）

### 示例对照
| 场景 | 判定 | 原因 |
|------|------|------|
| `useTicketList`：加载列表 + 五态 + 竞态 | 合规 | 单一关注点，可单测 |
| `useTicketRowOperations`：删除/关闭/优先级 三个行操作 | 合规 | 同属"行操作"一个关注点 |
| `useTicketFormModal`：开关 + 回填 + 异步校验 + 提交 | 临界，需注释说明 | 4 个关注点，但共享同一份表单生命周期 |
| `usePageState`：列表数据 + 弹窗开关 + 详情缓存 | 不合规 | 关注点无关联，属搬运 |

## 三、组件拆分决策

### 决策流程
```
开始：发现组件复杂
  ↓
问：组件文件是否超过 300 行？
  ├─ 否 → 暂不拆分，继续观察
  └─ 是 ↓
问：是否有明确的独立区块（表格/表单/卡片）？
  ├─ 是 → 按区块拆分为子组件
  └─ 否 ↓
问：是否有重复的渲染逻辑？
  ├─ 是 → 提取为可复用组件
  └─ 否 ↓
问：是否有复杂的交互逻辑？
  ├─ 是 → 逻辑提取到 Logic，UI 保留在组件
  └─ 否 ↓
问：props 是否超过 8 个？
  ├─ 是 → 审视职责，拆分或合并相关 props
  └─ 否 → 重新审视是否真的需要拆分
```

### 量化标准
**必须拆分**：
- 组件文件超过 300 行
- props 超过 8 个必选参数
- 组件内状态变量超过 10 个
- 嵌套层级超过 5 层

复杂表单例外走 `frontend/rules/core-principles.md` 超标处理，拆分更复杂时可保持并在注释说明保留原因。

### props 计数规则
聚合对象计为 **1 个 prop**，但必须满足全部三条，否则按展开后的字段数计：

1. 对象内字段属于同一关注点（如同一张表单的状态），不是无关状态的拼盘
2. 该对象有具名 TypeScript 接口，且定义在 types/ 下可被复用
3. 组件对该对象整体消费或整体透传，不在组件内逐字段解构后各自处理

**禁止**：为规避 8 个上限，把无关联的 props 塞进一个 `options` / `config` 对象。
这只是把参数爆炸藏进类型里，判定时按字段数计并视为超标。

```typescript
// ✅ 同一关注点聚合，计 1 个
interface TicketFormViewModel {
  values: TicketFormValues;
  errors: ValidationErrors<TicketFormValues>;
  isSubmitting: boolean;
  isCheckingCode: boolean;
}
defineProps<{ visible: boolean; form: TicketFormViewModel }>();

// ❌ 无关状态拼盘，按 6 个字段计
interface Options {
  visible: boolean;
  tableRows: Ticket[];
  currentUser: SessionUser;
  theme: string;
  onClose: () => void;
  logs: TicketLog[];
}
```

**建议拆分**：
- 有明确可独立的区块
- 有可复用的渲染逻辑
- 不同区块职责明显不同

**暂不拆分**：
- 行数在 200 行以内
- 职责单一，难以再拆
- 拆分后更复杂（props 层层透传）

### 拆分原则
1. **按区块拆分**：头部/内容/底部，表格/筛选/分页
2. **按职责拆分**：展示组件/容器组件
3. **按复用拆分**：提取可复用的通用组件
4. **避免过度拆分**：不为拆而拆，保持可读性

## 四、复用抽象决策

### 决策流程
```
开始：发现重复代码
  ↓
问：这是第几处出现？
  ├─ 第 1 处 → 直接实现，不抽象
  └─ 第 2 处及以上 ↓
问：两处的需求是否完全一致？
  ├─ 否 → 暂不抽象，等第三处或明确共性
  └─ 是 ↓
问：抽象后是否比两份重复更简单？
  ├─ 否 → 保持重复
  └─ 是 → 提取抽象
    ↓
实施抽象
  ↓
替换所有调用点（不留重复实现）
```

### 判定标准
**完全一致**：
- 输入输出结构相同
- 核心逻辑流程相同
- 差异仅在配置参数（可参数化）

**部分一致**：
- 输入输出结构不同
- 核心逻辑有分支
- 差异无法通过参数配置

**抽象更简单**：
- 抽象后代码总量减少
- 调用方更简洁
- 不需要复杂的配置对象

### 抽象层级选择
| 重复类型 | 抽象方式 | 位置 |
|---------|---------|------|
| UI 渲染重复 | 提取组件 | src/components/ |
| UI 逻辑重复 | 提取 Hook | src/hooks/ |
| 业务逻辑重复 | 提取 Logic | src/logic/ |
| 接口调用重复 | 提取 Service | src/services/ |
| 工具函数重复 | 提取 Utils | src/utils/ |

## 五、组件自持状态决策

### 决策流程
```
开始：组件需要状态
  ↓
问：是否是基础表单控件？
  ├─ 是（Input/Select/Checkbox 等）→ 允许自持 UI 交互状态
  └─ 否 ↓
问：是否是业务组件？
  ├─ 是 → 不允许自持状态，通过 props 传入
  └─ 否 ↓
问：是否涉及数据请求？
  ├─ 是 → 不允许自持状态，通过 props 传入
  └─ 否 ↓
问：是否是复合组件（多个子组件组合）？
  ├─ 是 → 不允许自持状态，通过 props 传入
  └─ 否 → 审查具体场景，咨询用户
```

### 白名单（允许自持状态）
- Input / Textarea
- Select / Autocomplete
- Checkbox / Radio / Switch
- Slider / Rating
- DatePicker / TimePicker
- ColorPicker

### 黑名单（不允许自持状态）
- 业务列表组件
- 业务表单组件
- 业务卡片组件
- Modal / Drawer / Dialog
- Table / DataGrid
- 自定义复合组件

### 边界情况
| 组件类型 | 是否允许 | 说明 |
|---------|---------|------|
| Upload | 允许 | 文件选择状态可自持，上传进度通过回调 |
| Dropdown Menu | 允许 | 展开/收起状态可自持 |
| Accordion | 允许 | 折叠/展开状态可自持 |
| Tabs（纯展示） | 允许 | 当前 Tab 索引可自持 |
| Tabs（业务） | 不允许 | 需要保持状态或影响数据加载 |

## 六、错误处理决策

### 决策流程
```
开始：捕获到错误
  ↓
问：错误类型？
  ├─ 网络错误（超时/断网/5xx）→ 可重试
  ├─ 业务错误（4xx/业务码）→ 不可重试
  └─ 客户端错误（验证失败）→ 不可重试
    ↓
可重试错误：
  问：是否已重试 3 次？
    ├─ 否 → 指数退避后重试
    └─ 是 → 展示错误 + 手动重试按钮
    
不可重试错误：
  问：错误级别？
    ├─ 全局错误（登录过期）→ Modal 提示
    ├─ 页面错误（数据加载失败）→ 错误占位
    ├─ 表单错误（提交失败）→ 表单错误提示
    └─ 操作错误（删除失败）→ Toast 提示
```

### 详见
见 `frontend/rules/error-handling.md`「展示方式」：全局错误走 Modal 对话框、页面级错误走错误占位组件、表单错误走表单顶部错误提示、操作错误走 Toast 提示。

## 七、页面复杂度检查

### 决策流程
```
开始：实现页面功能
  ↓
检查 1：页面文件行数
  ├─ > 500 行 → 必须拆分
  ├─ > 300 行 → 建议拆分
  └─ ≤ 300 行 ↓
检查 2：页面内函数数量
  ├─ > 5 个 → 提取到 Logic
  ├─ 4 到 5 个 → 建议审视职责，职责不清即提取
  └─ ≤ 3 个 ↓
检查 3：页面内状态变量
  ├─ > 8 个 → 审视状态归属，可能需要 Store
  ├─ 6 到 8 个 → 建议审视归属，共享即上移
  └─ ≤ 5 个 ↓
检查 4：是否有业务逻辑
  ├─ 有（判断/计算/转换）→ 提取到 Logic
  └─ 无（仅数据传递）↓
通过检查
```

### 页面瘦身策略
1. **提取组件**：独立区块拆分为子组件
2. **提取 Logic**：业务逻辑移到 Logic 文件
3. **提取 Hook**：状态管理逻辑封装为 Hook
4. **提升状态**：共享状态移到 Store

## 八、API 调用决策

### 决策流程
```
开始：需要调用 API
  ↓
问：是否已有对应的 Service 方法？
  ├─ 是 → 按下方"调用位置"判定
  └─ 否 → 先创建 Service 方法，再判定调用位置
    ↓
问：调用位置在哪一层？
  ├─ Component → 仅限组件自身交互（上传/异步搜索/唯一性校验），
  │              业务数据加载禁止（判据见 `frontend/rules/core-principles.md`「FE-102 组件完全解耦原则」）
  ├─ Page → 禁止直连 Service，交给 Hook
  ├─ Hook → 允许直接调用 Service 加载数据
  ├─ Logic → 允许调用 Service
  └─ Service → 请求与数据转换的落点
```

**Hook 直连 Service 是允许的**（见 `frontend/rules/architecture.md`「规则」：仅允许两类跨层直连：Page/Component 直接调 Logic，Hook 直接调 Service）。
Hook 的职责是"取数 + 管 UI 状态"，Logic 的职责是"判定业务规则"；
强制让 Logic 转发一层不产生任何判定，只增加一层无意义包装。

界线在于：**Hook 里不写业务判断**。谁能删、什么状态可改、删完去哪一页，
这些一律下沉 Logic；Hook 只负责调用顺序、UI 状态与错误分流。

```typescript
// ✅ Hook 直连 Service 取数，判定交给 Logic
const result = await fetchTicketList(query.value, { signal });
if (isStale()) return;
state.value = resolveListState(result.data.list);   // 判定在 Logic
```

```typescript
// ❌ Logic 只做转发，不含任何判定——这层是纯包装
export function loadTicketList(query: TicketListQuery) {
  return fetchTicketList(query);
}
```

### 强制规则
- ❌ Page/Component 不能直接调用 axios/fetch
- ❌ Page 不直连 Service（交给 Hook）
- ❌ Component 不加载页面业务数据（自身交互类调用见 `frontend/rules/core-principles.md`「组件调用 Service 的边界」）
- ✅ Hook 可直接调用 Service 取数，但不写业务判断
- ✅ Logic 可调用 Service
- ✅ Service 是唯一的接口访问入口（唯一写请求代码的地方）

## 九、文件创建决策

### 决策流程
```
开始：需要创建新文件
  ↓
问：文件类型？
  ├─ 路由页面 → src/pages/
  ├─ 可复用组件 → src/components/
  ├─ UI Hook → src/hooks/
  ├─ 业务 Logic → src/logic/
  ├─ API Service → src/services/
  ├─ 全局 Store → src/store/
  └─ 类型定义 → src/types/
    ↓
问：是否需要子目录？
  ├─ 单文件功能 → 直接放在对应目录
  └─ 多文件模块 → 创建子目录
    ↓
命名规范：
  ├─ 组件/页面 → PascalCase
  ├─ Hook → camelCase (useXxx)
  ├─ Logic → camelCase (xxx.logic.ts)
  ├─ Service → camelCase (xxx.service.ts)
  └─ 类型 → PascalCase (Xxx.types.ts)
```

## 十、测试编写决策

### 决策流程
```
开始：代码实现完成
  ↓
问：代码类型？
  ├─ Logic → 必须测试（高优先级）
  ├─ Service → 必须测试（高优先级）
  ├─ 工具函数 → 必须测试

  └─ 简单组件 → 可选
    ↓
问：测试内容？
  ├─ 纯函数 → 测试输入输出
  ├─ 异步操作 → 测试成功/失败路径
  ├─ 状态变化 → 测试状态转换
  ├─ 边界情况 → 测试极值/空值/错误
  └─ 业务规则 → 测试关键分支
```
