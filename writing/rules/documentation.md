# 场景五：说明与操作文档写作规范（`writing/rules/documentation.md`）

路径基准：本文所有裸路径相对规范库根 `<SPEC_ROOT>` 解析。见 `<SPEC_ROOT>/README.md`「路径基准」。

适用范围：产品使用手册、SOP 标准作业程序、操作指南、API/配置参考、FAQ、内部知识库。
理论底座：Diátaxis 四象限文档框架（Canonical/Ubuntu、Cloudflare 等数百个大型工程项目采纳）+ Google 开发者文档风格指南 + Microsoft 写作风格指南。

## 核心铁律：Diátaxis 四象限严格分离（严禁混写）

文档难懂的首要根因是“在一页里同时又教入门、又讲原理、又列全部参数”。动笔前必须先锁定本文档属于哪一个象限，并严守边界：

| 象限类型 | 读者当下目的 | 写法标准 | 严禁混入的内容 |
|---|---|---|---|
| **1. 入门教程（Tutorial）** | 零基础学着跑通第一个结果 | 手把手带读者从零走完一条安全最短路径，保证每一步都能看到即时正向反馈 | 严禁中途分叉讲高级选项、底层原理或边界异常 |
| **2. 操作指南（How-to Guide）** | 带着明确目标来解决具体问题 | 标题用动词/问题式（如“如何导出报表”）；直给前置条件 + 编号步骤 + 验收结果 | 严禁从头教基础概念或大段铺陈设计哲学 |
| **3. 参考手册（Reference）** | 工作中快速查参数、接口、状态码 | 客观、中立、结构与产品/代码一一对应；优先用标准表格（名称/类型/必填/默认值/说明） | 严禁混入教学口吻、个人观点或营销宣传语 |
| **4. 原理解释（Explanation）** | 脱离手头操作，想理解“为什么这样设计” | 讲清背景、权衡取舍、架构概念与替代方案对比 | 严禁塞入零碎操作步骤或大段配置清单 |

若读者需要跨象限信息，**只放超链接跳转**，不在当前页强行内联展开。

## 可执行编写标准（Google / Microsoft 风格共识）

1. **祈使句与第二人称**：操作步骤一律用祈使句直接动词起手（“点击 **保存**”，不写“用户此时可以进行保存操作”）；称呼读者统一用“你”，不混用“用户/大家/操作员”。
2. **一步一动作，结果可验证**：编号步骤每步只放 1 个核心动作；关键步骤后写明**预期可见结果**（如“页面右上角出现绿色提示：已生效”），方便读者自查是否做对。
3. **术语绝对一致**：同一个按钮、菜单、概念在全文只用唯一名称并加粗标注，绝不前半篇叫“提交”、后半篇叫“确认发布”。
4. **先给前提与风险警示**：涉及不可逆删除、权限变更、费用产生或停机窗口的操作，必须在步骤**之前**给出醒目风险提示，绝不放在步骤末尾马后炮。

## 禁止事项

- 禁止在步骤中省略关键前置条件（权限、版本、环境变量、数据准备）。
- 禁止使用“很简单、显然、只需轻松点击”等居高临下的措辞（当读者卡住时这类词会极大挫败体验）。
- 禁止把参考手册写成散文长段落，凡是 ≥ 3 项并列参数必须列表格。
